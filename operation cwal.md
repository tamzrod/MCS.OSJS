# Operation CWAL

## Entry and authority
Identify actual agent/runtime through `AGENTS.md` and `workflow/IDENTITY_MAP.md`; read root `handoff.md`, the approved queue, `planning/microtask/rules.md`, and the appropriate role adapter. Only explicitly human-approved, promoted packets in the named non-retired queue are eligible. Planning files, obsolete OTR packets, archives and evidence are never execution authority. If handoff is NONE or the queue is retired/missing, report NO ACTIVE QUEUE and STOP. A human-approved queue invocation authorizes processing its eligible tasks continuously, not creating new tasks or expanding permissions. Never infer approval from files merely being present.

## Exhaustive exam-style queue loop — attempt what is executable; account for every question
The goal of one invocation is to exhaust all currently executable approved work assigned to this agent, then give a reason for every approved task not completed. Treat the approved queue like an exam: attempt each answerable question once, write down why an unanswerable question cannot be answered, and move to the next independent question. Never guess an answer, fabricate evidence, bypass a prerequisite or stop merely to ask which question to attempt next. A task becoming ACTIVE is authorization to execute its existing packet immediately, not an invitation to request confirmation. Do not offer execute/pause/choose-next menus.

1. Inventory every approved queue ID and inspect queue metadata and packet headers for every nonterminal task (ID, status, blockers, assigned agent, stage). Do not read all packet bodies: open only the selected packet and necessary prerequisite/evidence references. Reject duplicate IDs, missing/retired blocker IDs, cycles, inconsistent queue/handoff state or unapproved packets. If integrity cannot be safely reconciled from authoritative evidence, checkpoint the precise integrity blocker and stop mutation; still report the disposition of every queue ID without inventing status.
2. Validate existing COMPLETE claims against the packet's required evidence and delivery; a label or evidence filename alone is not proof. Preserve valid completed work. If a completion claim is unsupported, record the discrepancy and reconcile only with permitted evidence-backed metadata changes; never silently downgrade, overwrite or fabricate evidence. An unresolved integrity discrepancy blocks affected tasks, not a license to execute dependents.
3. Classify every unfinished task: EXECUTABLE (prerequisites evidenced COMPLETE, correct agent, complete packet and all safety/authority gates); WAITING DEPENDENCY (list exact prerequisite IDs and their real outcomes); NEEDS OTHER AGENT (name assigned role and handoff); MISSING AUTHORIZATION/INPUT (identify exact missing instruction); or INTEGRITY BLOCKED (identify conflicting files/claims). `Blocker Task: NONE` removes task dependencies only. A task is eligible when PENDING/READY, every prerequisite is evidenced COMPLETE and its agent, environment and permissions satisfy all gates. Use lowest stable Task ID as deterministic selection default. Do not mark a dependent task attempted if its prerequisite failed.
4. Select one EXECUTABLE task and checkpoint exactly it ACTIVE in packet, queue and root handoff. If a task is already validly ACTIVE for this agent, resume it immediately rather than asking permission or activating another. Execute only its exact authorized actions; capture real commands, outputs, acceptance evidence and required delivery. Record actual permitted terminal outcome COMPLETE, FAIL or BLOCKED consistently, clear ACTIVE, and rescan. COMPLETE requires all packet acceptance and independent gates; no invented PASS. If interrupted, preserve truthful in-progress state for resumption, not a false terminal verdict.
5. After EACH task outcome or identified task-specific blocker, rescan the entire approved queue and execute the next independent eligible task. A FAIL/BLOCKED prerequisite leaves its dependents PENDING with explicit dependency reasons. Do not retry FAIL/BLOCKED tasks in the same invocation without separate authorization; attempt each task at most once per invocation. A missing build command for one task, another agent's task, or a failed dependency must never halt unrelated eligible work. No questions about already-approved activation or next-task selection.
6. Stop this runner only when every task is accounted for and no executable task remains for its actual role, or a genuine global safety/integrity issue prevents safe mutation. A required other-agent handoff is recorded and skipped while other tasks for this agent remain; hand off when this agent's runnable work is exhausted. Do not treat PENDING or BLOCKED as COMPLETE, and do not declare the whole queue finished while unresolved work exists. Persist accurate checkpoint and handoff for the next authorized runner.

## Mandatory final coverage report — every approved task, no omissions
At the end, enumerate EVERY approved queue ID exactly once with: ID, actual status, whether attempted in this invocation, evidence/report/commit reference if completed, or the precise reason it could not be executed or completed. Distinguish FAILED execution from NOT ATTEMPTED due to dependency, missing authorization, wrong agent, unsafe environment, or integrity. For dependency chains, name the blocking IDs and their underlying reasons. Include totals, next required actor/action for unresolved items, current branch/HEAD and delivery status when applicable. If a task was already COMPLETE before invocation, mark it previously completed rather than claiming it was executed now. A question/menu is not a substitute for this report.

## Role and safety gates
A continuous queue run does not grant a new agent identity or override per-packet role separation. OpenCode may execute its authorized CODE/DISCOVERY/DESIGN packets using `workflow/adapters/opencode.md`. Independent JR TEST/VERIFY requires the designated independent runner and its complete activated packet; OpenCode cannot impersonate JR or mark its own tests independent PASS. If the current agent cannot perform a task, leave it PENDING with an explicit role/authorization obstacle and continue other eligible tasks. If a role handoff requires another session, checkpoint and STOP that runner only after exhausting its other eligible work. No role edits ICC except through separately authorized BLACK SHEEP WALL. No destructive cleanup, production access, unrelated edits, merges, force push or main push without exact separate authority.

## JR lifecycle — applies separately to each selected TEST/VERIFY packet
JR requires a complete current packet naming goal, target, safe environment, pinned source and activation revision, exact commands and expected results, raw evidence, post-check, verdict rules, report path/schema, report-only commit, non-force push/ref and remote delivery verification. Thin, chat-only, stale, mismatched or incomplete packets are BLOCKED for that task; record and rescan for other eligible work permitted to this agent.

Before testing verify exact worktree, branch, clean state, packet ACTIVE status, source ancestry and current remote SHA using `git ls-remote`. Never repair stale state by autonomously fetching, switching, resetting, cleaning, restoring, rebasing or merging. Run authorized product tests once; stop that task on first failed gate. Capture exact commands, exit codes and full stdout/stderr or packet-approved durable transcript. Perform safe required post-check even after FAIL. Never rerun tests to force PASS.

JR cannot edit product source, configuration, manifests, task content beyond explicitly authorized lifecycle metadata, ICC or directives. Its only product-work write exception is the exact packet-named report; if the packet prohibits lifecycle metadata edits, a separately authorized queue coordinator records the verdict. Verify changed and staged product-work paths equal that report alone. Commit report, verify remote has not advanced, push non-force to specified branch and independently verify remote SHA. If delivery fails, report INCOMPLETE with underlying test result preserved; do not mark COMPLETE. An OpenCode self-test is not independent JR PASS.

PASS requires every packet check directly observed. Contradicted expectation means FAIL; unavailable authority, unsafe environment, stale source or missing mandatory evidence means BLOCKED. Missing report, post-check or required delivery means INCOMPLETE and must be recorded as an unresolved delivery obstacle, not COMPLETE. Finish the current task's evidence and checkpoint before rescan; never bypass a required independent verification gate.
