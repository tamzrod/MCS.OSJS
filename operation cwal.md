# Operation CWAL

## Entry and authority
Identify actual agent/runtime through `AGENTS.md` and `workflow/IDENTITY_MAP.md`; read root `handoff.md`, the approved queue, `planning/microtask/rules.md`, and the appropriate role adapter. Only explicitly human-approved, promoted packets in the named non-retired queue are eligible. Planning files, obsolete OTR packets, archives and evidence are never execution authority. If handoff is NONE or the queue is retired/missing, report NO ACTIVE QUEUE and STOP. A human-approved queue invocation authorizes processing its eligible tasks continuously, not creating new tasks or expanding permissions. Never infer approval from files merely being present.

## Continuous dependency-aware queue loop
1. Inspect queue metadata and packet headers for every nonterminal task (ID, status, blockers, assigned agent, stage). Do not read all packet bodies: open only the selected packet and necessary prerequisite/evidence references. Reject duplicate IDs, missing/retired blocker IDs, cycles, inconsistent queue/handoff state or unapproved packets; record the issue and STOP if queue integrity cannot be established.
2. A task is eligible when PENDING/READY, every listed prerequisite is COMPLETE with required independently verified evidence, and its packet, agent, environment and permissions satisfy all gates. `Blocker Task: NONE` removes task dependencies only. Pick any eligible task; use lowest stable Task ID as deterministic default, not as a dependency. If a desired task has unmet prerequisites, process an eligible prerequisite first or choose another eligible independent task. Never execute a dependent task early.
3. Mark exactly one selected task ACTIVE in its packet, queue and handoff, with a consistent checkpoint, before executing. Never run tasks concurrently. Follow that packet's exact scope and authorized actions; capture actual commands, outputs and evidence. Record its permitted terminal outcome COMPLETE, FAIL or BLOCKED in packet/queue/handoff, perform its delivery and remote checks, and clear ACTIVE before selecting another task. COMPLETE requires all packet acceptance and required independent gates; do not invent PASS.
4. Rescan the queue after each terminal result. Continue with another eligible independent task or prerequisite even if the prior task FAILed or BLOCKED. A FAIL/BLOCKED prerequisite keeps dependents PENDING and ineligible; record their dependency obstacle without pretending they were attempted. Do not retry a FAIL/BLOCKED task in the same invocation without separate explicit authorization. Each task is attempted at most once per invocation.
5. Stop only when every approved task is terminal, or no eligible task remains. Report counts and IDs for COMPLETE, FAIL, BLOCKED and remaining PENDING, with the exact blocker chain or safety/authority reason for each remainder. Never label the queue wholly COMPLETE while unresolved tasks remain. Persist an accurate handoff/checkpoint so a later authorized invocation can resume; do not silently start a new queue.

## Role and safety gates
A continuous queue run does not grant a new agent identity or override per-packet role separation. OpenCode may execute its authorized CODE/DISCOVERY/DESIGN packets using `workflow/adapters/opencode.md`. Independent JR TEST/VERIFY requires the designated independent runner and its complete activated packet; OpenCode cannot impersonate JR or mark its own tests independent PASS. If the current agent cannot perform a task, leave it PENDING with an explicit role/authorization obstacle and continue other eligible tasks. If a role handoff requires another session, checkpoint and STOP that runner; the approved queue may resume with the correct agent. No role edits ICC except through separately authorized BLACK SHEEP WALL. No destructive cleanup, production access, unrelated edits, merges, force push or main push without exact separate authority.

## JR lifecycle — applies separately to each selected TEST/VERIFY packet
JR requires a complete current packet naming goal, target, safe environment, pinned source and activation revision, exact commands and expected results, raw evidence, post-check, verdict rules, report path/schema, report-only commit, non-force push/ref and remote delivery verification. Thin, chat-only, stale, mismatched or incomplete packets are BLOCKED for that task; record and rescan for other eligible work permitted to this agent.

Before testing verify exact worktree, branch, clean state, packet ACTIVE status, source ancestry and current remote SHA using `git ls-remote`. Never repair stale state by autonomously fetching, switching, resetting, cleaning, restoring, rebasing or merging. Run authorized product tests once; stop that task on first failed gate. Capture exact commands, exit codes and full stdout/stderr or packet-approved durable transcript. Perform safe required post-check even after FAIL. Never rerun tests to force PASS.

JR cannot edit product source, configuration, manifests, task content beyond explicitly authorized lifecycle metadata, ICC or directives. Its only product-work write exception is the exact packet-named report; if the packet prohibits lifecycle metadata edits, a separately authorized queue coordinator records the verdict. Verify changed and staged product-work paths equal that report alone. Commit report, verify remote has not advanced, push non-force to specified branch and independently verify remote SHA. If delivery fails, report INCOMPLETE with underlying test result preserved; do not mark COMPLETE. An OpenCode self-test is not independent JR PASS.

PASS requires every packet check directly observed. Contradicted expectation means FAIL; unavailable authority, unsafe environment, stale source or missing mandatory evidence means BLOCKED. Missing report, post-check or required delivery means INCOMPLETE and must be recorded as an unresolved delivery obstacle, not COMPLETE. Finish the current task's evidence and checkpoint before rescan; never bypass a required independent verification gate.
